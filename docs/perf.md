# K1 Windows GPU 성능 기준값

2026-11-22, `main`의 `7a2cf76`을 도윤 PC에서 측정했어요. Windows 빌드 26300, Chrome 157.0.8103.79, Intel Arc B390(WebGL의 ANGLE Direct3D11), 1280 × 800, 픽셀 비율 1이에요. 로컬 HTTP에서 기존 페이지를 그대로 실행했고, 게임 파일은 수정하지 않았어요.

## 프레임 제한을 끈 재측정

같은 커밋과 GPU에서 Chrome에 `--disable-gpu-vsync --disable-frame-rate-limit`를 주고 다시 쟀어요. 1280 × 800, DPR 1에서는 장면마다 3회, 실제 크기에서는 장면마다 1회 측정했어요. 각 회차는 1초 안정화 후 4초예요. 표준 크기 열의 범위는 각 회차 통계의 최솟값과 최댓값이에요.

실제 크기 측정은 평소 Chrome에 저장된 최대화 상태를 별도 프로필에서 재현했어요. Chrome 외곽은 1440 × 852, 게임 영역은 1440 × 765 CSS 픽셀, 브라우저가 보고한 픽셀 배율은 200% (DPR 2), 캔버스는 2880 × 1530 픽셀이었어요. 화면 크기와 배율을 강제로 바꾸지 않았어요.

실제 크기의 캠핑장 걷기에서 가장 긴 간격은 123.3ms였어요. 이 표를 만들 때 측정 도구가 매 프레임 WebGL에서 GPU 이름까지 읽었어요. 아래 추적에서 이 조회가 긴 대기를 만들 수 있음을 확인했어요. 이 표는 당시 기록이며, K2에서 전후를 비교할 때는 GPU 이름을 한 번만 조회하는 도구로 기준값을 새로 재야 해요.

## 캠핑장 걷기 123.3ms 추적

같은 커밋과 Arc B390, 최대화한 Chrome 1440 × 765(DPR 2), 같은 프레임 제한 해제 옵션으로 반복했어요. 매번 캠핑장 입구의 같은 위치에서 `W`를 누르고 4초간 `requestAnimationFrame` 간격을 쟀어요. Chrome 기록을 켜면 측정 부하가 달라질 수 있어 결과를 나눴어요.

| GPU 이름 조회 | Chrome 기록 | 횟수 | 평균 범위(ms) | p99 범위(ms) | 가장 긴 간격(ms) | 100ms 이상 나온 회차 |
|---|---|---:|---:|---:|---:|---:|
| 매 프레임 | 끔 | 3 | 4.44–6.12 | 11.9–17.8 | 138.0 | 2/3 |
| 매 프레임 | 켬 | 5 | 4.55–5.24 | 9.5–13.4 | 48.2 | 0/5 |
| 시작 때 한 번 | 끔 | 3 | 2.84–4.49 | 31.6–114.5 | 141.0 | 1/3 |

- **재현**. 이전 방식에서 135.7ms와 138.0ms가 나왔고, GPU 이름을 시작할 때 한 번만 읽어도 141.0ms가 나왔어요. 기존 123.3ms의 정확한 원인은 당시 Chrome 기록이 없어서 확정할 수 없어요.
- **추적에서 확인한 측정 도구의 영향**. 기존 방식의 47.2ms 구간에서 렌더러 메인 스레드는 `GLES2::GetString` → `ImplementationBase::WaitForCmd`에서 약 39.3ms 기다렸고, GPU 프로세스의 `DXGISwapChainImageBacking::Present` 약 41.1ms와 겹쳤어요. 48.2ms 구간에서도 GPU 이름 조회의 대기와 화면 표시 작업이 겹쳤어요. 이 GPU 이름 조회는 게임의 매 프레임 작업이 아니라 측정 도구가 더한 호출이에요.
- **남은 원인**. GPU 이름을 한 번만 읽는 조건의 Chrome 기록은 스트림과 이벤트 방식 모두 내보내기가 완료되지 않았어요. 141.0ms가 나온 회차의 프레임 간격은 남았지만 Chrome 내부 기록은 없어요. GPU 이름 조회는 일부 대기를 설명하나, 재현된 100ms 이상의 간격을 게임 계산이나 GPU 표시 작업 중 어느 쪽 탓으로 돌릴 근거는 아직 없어요.

## 같은 걷기를 다시 재는 도구

`node tools/perf-walk.cjs --native --uncapped`를 실행하면 설치된 Chrome에서 캠핑장 걷기를 세 번 재고 회차마다 JSON 한 줄을 출력해요. `--native`는 창을 최대화하고 Windows 배율을 그대로 쓰며, `--uncapped`는 Chrome의 VSync와 프레임 제한을 끄는 옵션이에요. C2의 시험 손잡이(`window.__soft`, PR #5)가 필요해요. K6의 의존성 파일(PR #6)이 들어온 뒤에는 `npm --prefix tools ci`로 준비할 수 있어요.

PR #8의 새 자리에서는 `--spot beach`, `--spot spring`, `--spot rain`, `--spot chimes`를 붙이면 돼요. 시험 도구가 E를 눌러 앉고, 카메라와 배경이 안정되도록 3초 기다린 뒤 4초간 재요. 기본 브라우저 설정과 비교하려면 같은 명령에서 `--uncapped`를 빼요.

이 도구는 GPU 이름을 각 회차 시작 때 한 번만 읽어요. PR #5의 `9988058`에서 실제 게임 영역 1440 × 765, DPR 2로 세 번 실행했어요. 평균은 2.71–3.10ms, p99는 14.10–66.10ms였고 첫 회에 122.3ms 간격이 있었어요. 이 측정에서도 긴 간격이 다시 나왔지만 원인을 알 수 있는 Chrome 실행 기록은 남기지 않았어요.

### Chrome 기록을 다시 저장한 결과

GPU 이름을 한 번만 읽고 Chrome 기록 범위를 줄인 뒤, 시험 탭을 닫고 기록을 내보냈어요. 기존 성능 기준과 같은 `7a2cf76` 게임으로 최대화한 Chrome에서 같은 길을 4초씩 걸었어요.

| Chrome 조건 | 횟수 | p99 범위(ms) | 가장 긴 간격(ms) |
|---|---:|---:|---:|
| 기본 설정 | 3 | 16.9–17.3 | 18.0 |
| 프레임 제한 해제 | 5 | 6.2–53.3 | 71.5 |
| 프레임 제한 해제 + DirectComposition 끔 | 3 | 8.4–105.6 | 141.2 |

일반 합성 경로에서 나온 71.5ms 구간 중 렌더러는 GPU 명령 버퍼의 빈자리를 약 70.0ms 기다렸고, GPU 스레드의 화면 표시(`DXGISwapChainImageBacking::Present`)가 약 70.1ms 겹쳤어요. DirectComposition을 끈 비교에서도 141.2ms 구간 중 명령 버퍼 대기가 약 140.2ms였고, GPU 스레드에는 그 구간 전체에 걸친 WebGL 명령 처리(`CommandBuffer::Flush`)가 기록됐어요. 이번 기록은 두 조건에서 모두 브라우저의 GPU 명령 처리 대기가 길어진 곳까지 보여 줘요. 최초 123.3ms 회차의 기록은 없어서 같은 원인이었는지와 GPU 쪽에서 어느 작업이 지연을 시작했는지는 아직 확인하지 못했어요.

DirectComposition 끄기는 원인 분리를 위해 시험용 Chrome에서만 사용했어요. 기본 설정에서는 이번 세 회 모두 18ms 안에 들어왔으므로, K2에서 사용자 체감 성능을 비교할 때 기본 Chrome 결과와 프레임 제한 해제 결과를 따로 남겨요.

## 먼저 따로 재 볼 세 가지

기본 설정에서 평균은 모두 약 60 FPS였어요. 아래는 장면별 작업량을 보고 고른 후보예요. GPU와 CPU 시간을 함수별로 분리하지 않았으므로 실제 병목 순위나 개선 폭은 아직 알 수 없어요.

1. **해변 그리기 호출**. 최대 578회로 가장 많았어요. 같은 재질의 정적 장식을 묶을 수 있는지 비교하면 CPU의 그리기 명령 부담을 줄일 수 있어요. 배치 후에도 위치와 투명 물체의 그리기 순서가 같으면 모습은 유지돼요.
2. **불멍 장면의 호출**. 433~441회로 두 번째였어요. 정적 장식과 움직이는 불꽃을 나눠 비용을 확인하고, 정적 부분부터 묶으면 불꽃 움직임을 유지하면서 호출을 줄일 수 있어요.
3. **공중샷의 넓은 시야**. 프레임당 약 29.8만 삼각형이었어요. 전나무처럼 멀리 있는 물체를 구역별로 묶어 가시 범위 밖 묶음만 제외하는 시험을 해볼 수 있어요. 거리별로 메시를 단순화하는 방법은 공중샷에서 실루엣이 달라질 수 있어 별도로 비교해야 해요.
