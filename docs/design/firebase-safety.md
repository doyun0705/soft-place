# K4 멀티플레이 공개 전 안전장치

## 현재 상태

`FIREBASE_DB_URL`이 비어 있어 지금은 같은 브라우저 탭끼리 만나는 시험 모드를 사용해요. 현재 Firebase 규칙은 인증된 사용자와 저장 경로의 주인을 연결하지 않아요. 공개 방 목록을 읽으면 플레이어 상태까지 함께 내려오고, 12명 제한은 브라우저가 방을 고를 때만 확인해요. 이 상태로 실제 Firebase를 연결하면 다른 사람의 상태와 방의 인원수를 서버에서 보호할 수 없어요.

## 제안

1. **닉네임 시작은 그대로 유지해요.** 실제 온라인 방에 들어갈 때만 Firebase 익명 인증을 사용해요. 플레이 상태는 인증 UID 아래에 탭별 세션으로 두고, 그 UID의 세션만 쓰거나 삭제할 수 있게 해요. 연결이 끊기면 서버가 자기 세션만 지우도록 등록하고, 재접속 뒤에는 다시 등록해요. 같은 브라우저의 두 탭을 따로 닫아도 남은 탭은 계속 보여야 해요. [인증과 규칙](https://firebase.google.com/docs/database/security/rules-conditions) · [연결 종료 처리](https://firebase.google.com/docs/database/web/offline-capabilities)
2. **방 입장과 플레이 상태를 나눠요.** 랜덤 방 목록에는 입장에 필요한 정보와 인원수만 둬요. 방 안의 움직임은 그 방에 입장한 사용자만 읽어요. 서버가 방 입장과 12명 제한을 한 번에 처리하고, 초대 코드를 입력한 사용자의 입장 요청도 서버가 확인해요. 현재 네 글자 화면은 유지할 수 있지만, 코드 확인에는 짧은 시간에 반복 요청이 들어오는 것을 막는 제한이 필요해요.
3. **보내는 내용과 속도를 제한해요.** 기존 위치와 이름 검사에 허용된 장식·이모티콘, 서버 시간에 가까운 시각, 잘못된 필드 거부를 추가해요. 같은 세션의 상태 갱신과 이모티콘 반복에는 서로 다른 제한을 둬요. 게임은 움직임 변경을 약 200ms마다 보내고 멈춰 있을 때도 약 3초마다 갱신하므로, 이 동작과 네트워크 재연결을 함께 시험해 제한값을 정해요. 세션을 새로 만들어 제한을 피하는 일을 줄이도록 입장 횟수도 UID 단위로 봐요. [규칙에서 사용할 수 있는 값](https://firebase.google.com/docs/reference/security/database/)
4. **연결 실패를 화면에 표시해요.** 인증이나 입장이 실패했을 때 온라인 방에 들어간 것처럼 보이지 않게 해요. 다시 시도하거나 혼자 시작할 수 있게 하고, 주소가 없는 개발 환경의 탭 시험은 계속 쓸 수 있게 해요.

## 다른 방법

| 입장 방식 | 인원 제한과 코드 방 | 비용과 범위 |
|---|---|---|
| Realtime Database만 사용하는 시험 | 방마다 쓰기 규칙이 허용하는 자리 번호를 12개로 고정하고, 비어 있는 자리 하나를 그 자리의 트랜잭션으로 잡아요. 별도 `members/UID` 기록은 자기 자리와 UID가 일치할 때만 허용하고, 방을 읽는 규칙도 회원 기록과 자리 주인이 함께 맞는지 확인해요. 브라우저가 보낸 인원수 숫자를 그대로 믿으면 안 돼요. | Spark에서 Realtime Database의 무료 사용 한도 안에서 작은 시험을 할 수 있어요. 방 번호를 반복 조회하는 횟수나 여러 익명 가입의 총량을 방 규칙만으로 제한하기 어려워서 초대한 사람과의 시험부터 해요. |
| 입장 요청을 서버에서 확인 | 입장과 정원을 같은 서버 트랜잭션에서 처리하고, 초대 코드 확인 횟수를 줄이고 제한할 수 있어요. 클라이언트는 멤버 목록을 수정할 권한이 없어요. | Cloud Functions에 배포하려면 Blaze 요금제가 필요해요. 별도 서버를 쓰면 그 서버의 운영비와 관리가 필요해요. 입장 서비스가 멈춰도 혼자 있기는 계속 열 수 있게 설계해요. |

Realtime Database의 트랜잭션에는 해당 위치의 읽기와 쓰기 권한이 필요해요. 시험안에서는 그 권한을 자리 단위에 주고, 방 전체에 쓰기 권한을 주면 아래 규칙으로 되돌릴 수 없는 점을 확인해요. [트랜잭션 문서](https://firebase.google.com/docs/database/web/read-and-write#save_data_as_transactions) · [규칙 상속](https://firebase.google.com/docs/database/security) · [사용 한도](https://firebase.google.com/pricing) · [Functions 배포 조건](https://firebase.google.com/docs/functions/get-started)

네 글자 초대 코드는 외우기 쉬운 대신 짧아요. 서버가 확인하는 방식은 짧은 코드의 확인 속도를 제한할 수 있어요. 입장 서버 없는 시험에서 길이를 늘리면 우연히 추측될 가능성을 줄일 수 있어요. 코드 길이와 공개 범위는 C6에서 함께 정해요.

익명 계정은 다시 만들 수 있어서 UID만으로 반복 가입을 모두 막을 수 없어요. 초대 코드를 받은 사람이 다시 전달할 수도 있어요. 이 설계는 쓰기 권한과 방 접근부터 제한하고, 신고나 이용자 차단 정책은 기획에서 따로 정해요.

## 확인 순서

1. 로컬 Firebase 에뮬레이터에서 인증 없이 읽기·쓰기, 다른 사람 상태 수정·삭제, 가입하지 않은 방 읽기, 잘못된 필드·빠른 연속 갱신이 거부되는지 확인해요. [인증 에뮬레이터](https://firebase.google.com/docs/emulator-suite/connect_auth) · [데이터베이스 에뮬레이터](https://firebase.google.com/docs/emulator-suite/connect_rtdb)
2. 동시에 12명까지 입장하고 13번째 입장이 거부되거나 다른 랜덤 방으로 가는지 확인해요. 정상 이동, 이모티콘, 두 탭, 방 바꾸기, 창 닫기, 인터넷 끊기·재연결도 시험해요.
3. 준비된 시험용 Firebase에서 다른 브라우저 두 개로 실제 연결을 확인해요. 공개 주소는 보호 규칙과 동작이 확인된 뒤 별도 변경에서 검토해요.

## 현재 규칙을 에뮬레이터로 확인한 결과

PC에서 `main`의 규칙을 Realtime Database 에뮬레이터 4.11.2에 올려 가짜 계정과 상태로 8가지를 확인했어요. 지금 규칙의 동작을 기록한 결과예요. 아래에서 허용된 비로그인 쓰기와 다른 사람 상태 쓰기, 비회원의 코드 방 읽기는 새 규칙에서 거부해야 해요.

| 시도 | 현재 규칙 |
|---|---|
| 로그인 없이 공개 방 목록 읽기 | 허용 |
| 방에 가입하지 않은 계정이 코드 방 읽기 | 허용 |
| 로그인 없이 코드 방들의 전체 목록 읽기 | 거부 |
| 자기 위치를 정상 범위 안에서 바꾸기 | 허용 |
| 다른 계정의 위치 바꾸기 | 허용 |
| 로그인하지 않은 상태에서 위치 바꾸기 | 허용 |
| 위치 범위를 넘긴 상태 보내기 | 거부 |
| 정의되지 않은 필드를 상태에 추가하기 | 거부 |

### 제안한 권한 구조의 짧은 시험

프로젝트에 올리는 규칙과 분리한 시험 규칙으로 검증했어요. 가짜 계정의 방 멤버 목록과 UID 아래 탭별 세션을 만들었을 때, 입장한 계정만 상태를 읽고 자기 세션만 쓸 수 있었어요. 한 탭의 연결을 끊으면 그 탭 기록만 지워지고, 같은 UID의 다른 탭 기록은 남았어요. 서버 시각으로 보낸 값은 받아들였고 오래된 시각과 너무 빠른 연속 갱신은 거부했어요. 반복 확인이 쉬운 150ms를 시험에만 사용했어요. 실제 게임의 이동과 이모티콘으로 제한값을 정하는 일은 남아 있어요.

이 시험은 에뮬레이터의 가짜 인증 컨텍스트를 사용했어요. 실제 익명 로그인, 서버의 코드 확인과 12명 동시 입장, 닉네임 정책은 따로 검증해야 해요. 닉네임과 신고 등 화면·운영 결정은 C6 설계와 맞춰요. [C6 설계 PR](https://github.com/doyun0705/soft-place/pull/10)

시험에서 확인한 RTDB 상태 갱신 규칙의 일부예요. 이 조건은 별도의 UID 쓰기 규칙과 함께 적용해요. `t`는 서버 시각으로 보내고, 150ms는 이 시험의 값이에요.

```json
{
  ".validate": "newData.hasChildren(['x', 't']) && (!data.exists() || newData.child('t').val() >= data.child('t').val() + 150)",
  "t": {
    ".validate": "newData.isNumber() && newData.val() === now"
  }
}
```

### 뒤로 보낸 탭과 연결 종료

현재 20초 규칙은 애니메이션 프레임에서 보낸 갱신이 멈추면 상대 화면에서 지워요. Chrome은 숨긴 탭의 프레임을 멈추고 타이머도 늦출 수 있어요. 온라인 방에서는 서버의 세션 삭제를 퇴장의 기준으로 삼고, 숨은 탭은 마지막 위치에 멈춘 상태로 표시하는 안을 시험해요. 기록이 남은 채 탭이 실제로 종료되는 경우에는 `onDisconnect`가 제거하고, 재접속한 탭은 새 연결에 제거를 다시 등록해요. 20초 로컬 시험 동작과 온라인 방의 표시 방법은 별도로 시험해요. [Chrome 숨은 탭 동작](https://developer.chrome.com/blog/timer-throttling-in-chrome-88) · [Firebase 연결 종료 처리](https://firebase.google.com/docs/database/web/offline-capabilities)

실제 익명 인증을 붙일 때 기존 Firebase SDK와 같은 버전의 `firebase-auth-compat.js`를 사용하고, 이미 쓰는 Firebase CDN의 예외를 `AGENTS.md`에 기록하는 협의가 필요해요. 실패 화면 문구는 Claude, 연결 처리와 규칙은 Codex 범위예요.
